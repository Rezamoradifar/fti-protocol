# اتصال سرویس‌ها به دیپلوی تازهٔ FTI

قراردادهای شبکهٔ ۹۷ با source ثابت `bc2163070a6e79bcc129a6a788e61c4ace402bdf` و digest برابر `e2c54422e78d768bce0236379fe3047566ea01e465a1d8a81ce25c564ee053c1` قبلاً ساخته شده‌اند. [شواهد دیپلوی](PUBLIC_TESTNET_DEPLOYMENT_20261015.fa.md) ثبت شده است. برای اتصال سایت نباید `start-fresh-testnet.py` یا نصب‌کنندهٔ ساخت قرارداد را دوباره اجرا کرد.

اپراتور فعال بودن `fti-continuity-web.service` و `fti-continuity-keeper.service` با کاربر/گروه `fti-v3` را گزارش کرده است. Keeper از `/opt/fti/releases/continuity-a09b3f23a6ea3e7e82a6117e9a000aa82f0091ed` و environment قبلی اجرا می‌شود؛ وب یک drop-in به نام `90-frontend.conf` دارد. بنابراین ابزار جدید تنظیمات مؤثر هر پردازش را داخل سرور می‌خواند، نه اینکه مسیر نسخهٔ وب را حدس بزند.

## ابزار اتصال

`tools/activate-fresh-testnet.py` با Python استاندارد سیستم و Node 22 نصب‌شدهٔ خود سرویس کار می‌کند. فقط همین deployment موفق، آدرس‌ها، digest و شبکهٔ ۹۷ را می‌پذیرد.

1. خروجی موفق دیپلوی و build/tests آماده‌شده را کنترل می‌کند و تغییر فایل‌های tracked یا revision کاندید را رد می‌کند.
2. فایل‌های اجرای ساخته‌شده و وابستگی‌ها را به release جدید در `/opt/fti/releases` کپی می‌کند. `.git`، فایل‌های `.env`، دایرکتوری deployment خصوصی، کلید deployer و کلیدهای test-genesis به release عمومی کپی نمی‌شوند. build، نصب npm و دیپلوی مجدد لازم نیست.
3. تنظیمات مؤثر را خصوصی ذخیره می‌کند. RPC و WalletConnect موجود حفظ می‌شوند؛ کلید Keeper موجود فقط در environment سرویس Keeper باقی می‌ماند. environment جدید با دسترسی `0640` و دایرکتوری آن با `0750` برای `root:fti-v3` ذخیره می‌شوند. محتویات این فایل‌ها نباید منتشر شوند.
4. با UID واقعی سرویس، fingerprint کل source/build، hash کدها، implementationهای پراکسی، تراکنش‌های ایجاد، شورا و اتصال قراردادها را از RPC می‌خواند. نسخهٔ استخر و cap-flush باید ۱ و موجودی گس Keeper غیرصفر باشد. این مرحله امضاکنندهٔ متصل به شبکه نمی‌سازد و تراکنشی ارسال نمی‌کند.
5. هر دو سرویس قدیمی را متوقف می‌کند و با drop-in جداگانه، مسیر اجرا و deployment هر دو را تغییر می‌دهد. فایل‌های اصلی unit، environment و drop-in وب قبلی تغییر نمی‌کنند. تغییر Nginx فقط با گزینهٔ جداگانهٔ `--repair-api-routes` و طبق بخش زیر انجام می‌شود.
6. وب را راه‌اندازی و `/health`، `/api/config`، `/api/state` و assetهای واقعی را روی پورت ۳۱۱۰ بررسی می‌کند. HTTPS دامنهٔ `ftiprotocol.com` نیز باید deployment جدید و مدل `hourly-global-pool-v2` را نشان دهد.
7. پس از موفقیت وب، Keeper موجود را روی همین قراردادها فعال می‌کند. این سرویس برای پردازش عادی تست‌نت از موجودی گس فعلی خودش مصرف می‌کند؛ ابزار کیف‌پول جدید نمی‌سازد و هیچ کیف‌پولی را شارژ نمی‌کند. فعال و ثابت ماندن پردازش بررسی می‌شود؛ این به‌تنهایی اثبات پرداخت ساعتی نیست.

## اجرای داخل VPS

نسخهٔ منتشرشدهٔ ابزار را با URL حاوی commit ثابت و SHA256 بررسی‌شده دریافت کنید، سپس:

```bash
python3 /root/activate-fresh-testnet.py \
  --run-work /root/fti-fresh-testnet-runner/bc2163070a6e79bcc129a6a788e61c4ace402bdf/run-lmflrvzk
```

مسیر بالا همان اجرای موفق اپراتور است. اجرای موفق ابزار `FTI_FRESH_TESTNET_SERVICES_ACTIVE` و نتیجهٔ عمومیِ فاقد کلید چاپ می‌کند. اجرای دوباره، اگر هر دو سرویس همین deployment را داشته باشند و وب محلی و HTTPS صحیح باشد، بدون restart نتیجهٔ `ALREADY_ACTIVE` می‌دهد.

## اصلاح مسیر API روی همان دامنه و IP

اپراتور یک اجرای ناموفق را گزارش کرد که پس از تأیید وب محلی و پیش از فعال‌شدن Keeper جدید، در HTTPS با `Served deployment mismatch: usd` متوقف و سرویس‌های قبلی بازگردانده شدند. مقایسهٔ بعدی نشان داد پورت ۳۱۱۰ نسخهٔ `2afdc682b2eb4961b30e856b415f09d29fcda92d` را ارائه می‌کند، اما HTTPS محلی و عمومی نسخهٔ `81aae37e2ad3abcbe46d27ad48c8f89ba54610d5` را نشان می‌دهند. DNS برابر `185.114.206.44` بود و reload به‌تنهایی اختلاف را رفع نکرد.

خروجی Nginx وجود include اختصاصی `/etc/nginx/fti-fresh-api-routes.conf` را نشان داد. محتوای کامل این فایل هنوز در گفت‌وگو ارائه نشده است؛ ابزار جدید آن را روی خود سرور می‌خواند و فقط در صورت تطبیق با قواعد محدود زیر تغییر می‌دهد:

- `--repair-api-routes` گزینهٔ صریح برای همین وضعیت است. ابزار باید همان IP را در DNS دامنهٔ `ftiprotocol.com` ببیند؛ دامنه، IP و گواهی TLS تازه‌ای ایجاد نمی‌کند.
- فایل باید موجود، معمولی، متعلق به root و فقط از vhostهای شناخته‌شدهٔ FTI ارجاع شده باشد. تمام دستورهای `proxy_pass` آن باید صریح و به HTTP روی loopback با پورت سرویس باشند؛ مقصد خارجی، مقصد متغیر یا قالب ناشناخته پیش از توقف سرویس‌ها رد می‌شود.
- فقط میزبان/پورت مقصدهای این فایل به `127.0.0.1:3110` تبدیل می‌شوند. مسیر URI، locationها، احراز هویت، headerها، محدودیت‌ها، commentها و سایر فایل‌های سایت حفظ می‌شوند. فایل اصلی و فایل جایگزین با hash و دسترسی خصوصی بکاپ می‌شوند.
- پس از سلامت وب جدید، تغییر فایل به‌صورت atomic انجام، `nginx -t` اجرا و Nginx reload می‌شود. سپس آدرس‌ها، source fingerprint، مدل استخر و assetهای واقعی روی HTTPS دامنه بررسی می‌شوند. Keeper تنها پس از این بررسی‌ها شروع می‌شود.
- rollback این اجرا، فایل API قبلی را نیز برمی‌گرداند. اگر اپراتور پس از آماده‌سازی فایل را تغییر داده باشد، ابزار آن را بازنویسی نمی‌کند. نتیجهٔ عمومی فقط `httpsApiRoutesRepaired` را گزارش می‌کند؛ محتویات تنظیمات خصوصی چاپ نمی‌شوند.

برای اجرای این حالت، گزینهٔ `--repair-api-routes` را کنار `--run-work` به نسخهٔ ثابت و دارای hash جدید ابزار بدهید. قراردادهای جدید همان deployment موفق قبلی هستند. اپراتور اجرای موفق این حالت از نسخهٔ `75758023231681372a313f641f3afe0a1efabff8` را با نتیجهٔ `FTI_FRESH_TESTNET_SERVICES_ACTIVE` گزارش کرده و پاسخ عمومی دامنه نیز مستقل بررسی شده است؛ [شواهد اتصال موفق](PUBLIC_TESTNET_DEPLOYMENT_20261015.fa.md) را ببینید. پس از موفقیت، این دستور برای انجام تست پرداخت یا ساخت دوبارهٔ قرارداد اجرا نمی‌شود.

## بازگشت

پیش از توقف سرویس‌ها، ابزار `ROLLBACK_COMMAND` را با مسیر اختصاصی چاپ می‌کند. backup خصوصی در `/var/lib/fti-continuity/cutover-backups/` باقی می‌ماند. در خطاهای عادی، Ctrl+C یا سیگنال قطع SSH (SIGHUP) هنگام تغییر اتصال، drop-inهای جدید برداشته و سرویس‌های قبلی شروع می‌شوند؛ اگر ترمیم API فعال بوده، فایل Nginx قبلی نیز بازگردانده می‌شود. در صورت SIGKILL/قطع برق، دستور بازگشت ذخیره‌شده را اجرا کنید. rollback فایل‌هایی را که بعداً اپراتور تغییر داده باشد حذف نمی‌کند.

بازگشت، اتصال سرویس‌ها را برمی‌گرداند؛ تراکنش‌هایی که Keeper جدید قبلاً انجام داده است از بلاکچین حذف نمی‌شوند. قراردادهای قدیمی و جدید، receiptها و نشانگرهای دیپلوی حفظ می‌شوند. کاربران و موجودی‌های deployment قبلی به این deployment تازه منتقل نمی‌شوند.

## شواهد آزمون و محدودیت

سیزده آزمون محلی `python3 -B test/fresh-testnet-activation.test.py -v` موفق شدند. علاوه بر هفت آزمون اولیهٔ شبکه، اسرار، فایل‌های build و تغییر/بازگشت سرویس‌ها، شش آزمون تازه حفظ URI و سیاست‌های مسیر، رد مقصد خارجی/متغیر، محدودبودن ارجاع include به FTI، ترتیب ترمیم و بررسی HTTPS، بازگشت هم‌زمان Nginx و سرویس‌ها و حفظ ویرایش هم‌زمان اپراتور را کنترل می‌کنند. آزمون‌ها از فایل‌های واقعی موقت و systemd/Nginx/HTTP شبیه‌سازی‌شده استفاده می‌کنند. پس از این آزمون‌ها، اپراتور ابزار را روی VPS اجرا و خروجی موفق را ارائه کرده است؛ این دو نوع شاهد از هم متمایزند.

پس از اتصال، تست واقعی خرید و تسویه/پرداخت کامل استخر در ساعت بسته‌شده باید جداگانه روی همین شبکه ثبت شود. نتیجهٔ اتصال سرویس‌ها، موفقیت آن سناریو یا آمادگی مین‌نت را اعلام نمی‌کند.
