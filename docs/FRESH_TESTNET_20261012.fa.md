# راه‌اندازی تازهٔ FTI؛ بدون انتقال دادهٔ قبلی

کاربر روشن کرده است که داده، جایگاه و موجودی قراردادهای قبلی را برای راه‌اندازی جدید نمی‌خواهد. پرسش مهاجرت برای آزمایش امکان حفظ داده‌ها در آینده بوده است. بنابراین این مسیر به قرارداد تازه مربوط است؛ مهاجرت، ارتقای قرارداد قبلی، ادغام شبکه‌ها یا حذف سرویس قبلی انجام نمی‌دهد.

## قرارداد و امکانات

از همان منابع بررسی‌شدهٔ فعلی `FundedBinaryPlanUpgradeable.sol` و `FTIReserveTokenUpgradeable.sol` استفاده می‌شود؛ برای ساخت آدرس تازه، بازنویسی بی‌دلیل منطق مالی لازم نیست. اتوبای انتخابی ۵ تا ۱۰۰٪ از درآمد ساعتی باینری برای فرد واجد شرایط، حذف سقف قیمت اتوبای، درخواست بستن ماه با موعد اول ماه میلادی بعد و منطق توکن فعلی حفظ شده‌اند. این تغییر هیچ کارمزد، سهم صندوق، رتبه یا محدودیت خرید تازه‌ای وضع نمی‌کند.

راه‌اندازی، هفت قرارداد جدید شامل USD آزمایشی، شورا، Timelock، دو implementation و دو proxy ایجاد می‌کند و سپس اتصال باینری/توکن را در تراکنش هشتم انجام می‌دهد. هر پروکسی هم‌زمان با ایجاد اولیه مقداردهی می‌شود. نیازی به امضاهای شورای قرارداد قبلی برای ایجاد این مجموعه نیست. هفت آدرس عمومیِ منتخبِ شورای جدید باید صریحاً داده شوند؛ خود قرارداد شورای تازه همان ۵ از ۷ و Timelock با تأخیر ۷۲ ساعت را برای عملیات آینده حفظ می‌کند. این ابزار کلیدهای شورا را نمی‌سازد یا جمع‌آوری نمی‌کند.

**این نسخه تست‌نت است، نه شبکهٔ اصلی:** chain 97 و شبکهٔ محلی 31337 مجازند. پشتوانهٔ این نسخه MockUSD آزمایشی است، نه USDT واقعی. درخواست عمومی ایجاد نسخهٔ تازه، مجوز استفادهٔ این MockUSD روی شبکهٔ اصلی نیست.

**جزئیات Genesis را پنهان نمی‌کنیم:** initializer موجود ۳۱ جایگاه اولیه دارد؛ در این مسیر ولت دیپلوی‌کننده به‌علاوه ۳۰ ولت آزمایشی تازه ساخته می‌شوند. واحد خریداری‌شده، رتبه، اعتبار، پاداش، موجودی توکن و پشتوانهٔ شروع صفرند. این ۳۱ جایگاه، کاربران ۱۲۹/۱۸۰ نفرهٔ قبلی نیستند و هیچ کاربر قبلی وارد نمی‌شود. `--test-genesis` پذیرش صریح همین ساختار تستی است. فایل خصوصی test-genesis-keys.json فقط در پوشهٔ خروجی جدید نگهداری می‌شود؛ آن را به گیت‌هاب یا چت نفرستید. تک‌ریشه‌کردن یا تغییر تعداد جایگاه‌های اولیه موضوع متفاوتی است و در این ادامه اجرا نشده است.

## آماده‌سازی کد بدون دست‌زدن به سرویس فعلی

در checkout جداگانهٔ نسخهٔ بررسی‌شده:

```bash
npm ci
npm run compile
npm run build:web
npm --prefix landing run build
node --test --test-concurrency=2 test/fresh-testnet.test.mjs test/global-builder-controls.test.mjs test/global-frontend.test.mjs test/member-landing-theme.test.mjs
node scripts/fresh-testnet.mjs --help
```

یا `tools/prepare-fresh-testnet.sh` را با SHA کامل همان commit اجرا کنید. ابزار در پوشهٔ تازه زیر `$HOME/fti-fresh-candidates` دریافت و تست می‌کند؛ `FTI_FRESH_CANDIDATE_PREPARED` به معنی آماده‌بودن کد است، نه دیپلوی یا اتصال دامنه. Node 22 یا جدیدتر لازم است. نصب‌کننده هیچ سرویس، nginx، فایل deployment قبلی، کیف‌پول یا قرارداد را تغییر نمی‌دهد.

## مرحلهٔ اول: برنامهٔ استقرار بدون امضا

فایل NEW_DAO.json را بیرون checkout با threshold برابر 5 و آرایهٔ partners شامل هفت آدرس عمومی غیرصفر و غیرتکراری بسازید. ابزار عمداً فایل شورای قبلی را خودکار انتخاب نمی‌کند. قبل از استفاده مطمئن شوید صاحبان این آدرسها توان امضای عملیات آینده را دارند. هفت آدرس متمایز به‌تنهایی استقلال نگهداری هفت کلید را اثبات نمی‌کند.

```bash
export FTI_FRESH_RPC_URL='YOUR_TESTNET_RPC'
node scripts/fresh-testnet.mjs plan \
  --chain 97 \
  --deployer YOUR_PUBLIC_DEPLOYER_ADDRESS \
  --dao-file /private/NEW_DAO.json \
  --test-genesis \
  --out /private/NEW_FTI_RELEASE_DIRECTORY
```

مسیر خروجی باید تازه باشد، parent آن باید از قبل وجود داشته باشد و خارج از checkout باشد. مقدار `digest` چاپ‌شده را پس از بررسی plan.json نگه دارید. این مرحله امضا نمی‌کند و قرارداد نمی‌سازد؛ آدرس‌های موجود در plan صرفاً پیش‌بینی بر مبنای nonce هستند، نه آدرس نصب‌شده. اعضای شورا، root/development، Genesis، bytecode، مقداردهی اولیه، نسخهٔ کد و مقصد تنها فراخوانی bind باید بررسی شوند. استقرار قبلی ورودی این برنامه نیست.

## مرحلهٔ دوم: ارسال صریح به شبکهٔ آزمایشی

فقط بعد از بررسی plan، ولت دیپلوی‌کننده و بودجهٔ گس:

```bash
node scripts/fresh-testnet.mjs deploy \
  --out /private/NEW_FTI_RELEASE_DIRECTORY \
  --send --confirm-plan DIGEST_PRINTED_BY_PLAN \
  --key-file /private/testnet-deployer.key \
  --max-fee-wei YOUR_TOTAL_APPROVED_GAS_BUDGET_WEI \
  --max-gas-price-wei YOUR_APPROVED_GAS_PRICE_CEILING_WEI \
  --confirmations 2
```

کلید فقط از فایل خصوصی 0600 خوانده می‌شود. مقادیر بالا نمونهٔ نام فیلدند، نه آدرس یا بودجهٔ ساخته‌شده. لازم نیست کلید خصوصی، seed phrase یا توکن RPC در چت منتشر شود. انتقال native coin به مقصد در تراکنش‌های این ابزار صفر است؛ هزینهٔ گس از ولت دیپلوی‌کننده پرداخت می‌شود. بودجه هر مرحله قبل از ارسال رزرو می‌شود، سقف تعداد تراکنش هشت و سقف gas هر تراکنش ۱۲ میلیون است. بودجه مربوط به همین اجراست، نه تضمین هزینهٔ آیندهٔ Keeper یا کاربران.

ابزار plan را با build و تنظیمات فعلی بازسازی می‌کند و calldata دلخواه داخل فایل را کورکورانه امضا نمی‌کند. تغییر nonce، شبکه، امضاکننده، کد، برنامه یا وجود تراکنش معلق باعث توقف می‌شود. مرحله و هش تراکنش قبل/بعد از دریافت رسید در journal.jsonl ثبت می‌شوند. فایل deployment.started.json از اجرای تصادفیِ تکراری جلوگیری می‌کند و خودکار حذف نمی‌شود.

**هشت تراکنش، یک تراکنش اتمیک واحد نیستند.** خطا یا قطع ارتباط در میانه می‌تواند چند قرارداد تازهٔ نیمه‌تمام باقی بگذارد. آن‌ها قراردادهای قدیمی را تغییر نمی‌دهند، اما گس مصرف‌شده برنمی‌گردد. ابزار resume خودکار ندارد؛ فایل started را پاک نکنید و کورکورانه دوباره اجرا نکنید. ابتدا journal و nonce و رسیدها بررسی شوند. وضعیت FAILED_OR_PARTIAL_DEPLOYMENT را موفقیت حساب نکنید.

## نتیجه و اتصال به سایت

فقط موفقیت تمام تراکنش‌ها، تطبیق ایجاد/آدرس/هش کد، نقش‌ها و حالت اولیه نتیجهٔ `FTI_FRESH_TESTNET_DEPLOYED` را می‌دهد. deployment.json شامل دادهٔ معتبر همان قراردادهای تازه برای server.mjs است؛ initialState در بلوک bind ثبت می‌شود. قیمت spot با عرضهٔ صفر برابر صفر است و نرخ خرید شروع ۰٫۱۰ جداگانه در bootstrapQuotePrice ثبت می‌شود؛ این دو نباید یک عدد گزارش شوند.

از کد همان checkout برای وب و Keeper استفاده شود؛ تغییر sourceFingerprint یا کپی‌کردن deployment قدیمی لازم نیست. پیش از جابه‌جایی دامنه، وب جدید را روی پورت محلی آزاد و جدا با همین deployment اجرا و health/config/state/ABI را بررسی کنید. فعال‌سازی Keeper نیازمند کیف‌پول گس، تنظیمات و پایش جداست؛ درخواست زودهنگام ماه به معنی اجرای تراکنش در نیمه‌شب بدون Keeper نیست. این بسته nginx، systemd، دامنه یا پورت ۳۱۰۸/۳۱۱۰ را خودکار عوض نمی‌کند.

## شواهد و مرز ایمنی

تست تازه دو مجموعهٔ جدا روی Ganache می‌سازد: مجموعهٔ اول خرید، موجودی و پاداش غیرصفر دارد؛ مجموعهٔ دوم با صفر بودن حسابداری/مطالبات و بدون عضویت کاربر مجموعهٔ اول ساخته می‌شود. اطلاعات و موجودی مجموعهٔ اول قبل و بعد برابرند. انتخاب اتوبای ۱۰۰٪، رد درصد نامعتبر، درخواست زودهنگام ماه بدون تسویه و API واقعی وب جدید بررسی می‌شوند. آزمون CLI نیز plan/deploy واقعیِ محلی، فایل‌های خصوصی، journal و رد اجرای تکراری را آزمایش می‌کند.

این آزمایش محلی، دیپلوی روی BNB عمومی یا تضمین امنیت همه‌جانبه نیست. یک اشکال در برچسب CONFIRMED گزارش تراکنش طی تست پیدا و اصلاح شد؛ تست دست‌نخورده باقی ماند. نتیجهٔ اجرای کامل و CI همان commit در توضیح PR ثبت می‌شود، نه از روی صرف وجود فایل تست. نخستین اجرای کامل در ابزارِ ۴۵ثانیه‌ای قطع شد؛ فقط اجرای بعدیِ تکمیل‌شده باید به‌عنوان شواهد گزارش شود.

تست‌های مهاجرت و خروجی کاربران از مخزن حذف نشده‌اند، اما در مسیر راه‌اندازی تازه اجرا یا به‌عنوان ورودی مصرف نمی‌شوند. آیندهٔ بازیابی به سازگاری storage، امنیت کلیدهای شورا، پشتوانه، خروجی قابل‌راستی‌آزمایی و آزمون مستقل نیاز دارد؛ قابلیت ارتقا تضمین بازیابی پول در هر نوع خرابی نیست. هشدارهای وابستگی و ممیزی مستقل همچنان جدا از نتیجهٔ تست‌ها هستند.
