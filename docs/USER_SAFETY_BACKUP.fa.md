# خروجی خصوصی کاربران برای آمادگی بازیابی

درخواست مالک، ذخیره و بررسی وضعیت کاربران برای خرابی احتمالی است؛ نه ادغام شبکه، انتقال پول، freeze یا ارتقای فوری. ابزار `tools/backup-users-state.py` با یک اجرای صریح روی سرور موجود، snapshot داده‌های زنجیره‌ای را می‌گیرد. این سند مدرک گرفته‌شدن بکاپ کاربران واقعی نیست؛ تا فرمان روی سرور اجرا و result.json موفق دریافت نشود، چنین ادعایی وجود ندارد.

## اجرا

از نسخهٔ ثابت کد استفاده کنید. فایل Python فعلی دارای SHA-256 زیر است:

`f76caeee611a9fdb27ef2597d31c2134d8a8c3fd1ffcd61ef64d31422f00438e`

```bash
(
  set -euo pipefail
  umask 077
  REV='017beb8804f7d1f25bc4c7115d7af90e4a83ea49'
  FILE="$(mktemp /root/fti-users-backup.XXXXXX.py)"
  curl -fL --retry 2 --connect-timeout 15 --max-time 120 \
    "https://raw.githubusercontent.com/Rezamoradifar/fti-protocol/$REV/tools/backup-users-state.py" -o "$FILE"
  printf '%s  %s\n' 'f76caeee611a9fdb27ef2597d31c2134d8a8c3fd1ffcd61ef64d31422f00438e' "$FILE" | sha256sum -c -
  python3 -I "$FILE" --ports 3110 3108
)
```

روی همان سرور با root اجرا شود. برنامه از پورت‌ها PID و مسیر server.mjs واقعی را شناسایی می‌کند؛ فقط سه نسخهٔ کد سرور بازبینی‌شده را می‌پذیرد. کلید خصوصی، seed، فایل .env یا environ پردازش را نمی‌خواند. منبع صادرکننده از نسخهٔ ثابت گیت‌هاب دریافت و هش Git blob آن کنترل می‌شود. کتابخانه‌های موجود ethers و solc همان نصب لازم‌اند؛ npm install اجرا نمی‌شود. استاندارد JSON-RPC پارامتر بلوک را برای خواندن وضعیت مشخص می‌کند: https://ethereum.org/developers/docs/apis/json-rpc/ .

## دادهٔ ذخیره‌شده

هر دو دفتر عضویت جدا می‌مانند؛ هیچ حساب مشترکی ادغام نمی‌شود. بلوک ثابت مشترک، بیست بلوک عقب‌تر از کوچک‌ترین head گزارش‌شده انتخاب و هش آن در هر دو مسیر مقایسه و در پایان دوباره بررسی می‌شود. این فاصله ادعای finality نیست. در اجرای دوپورتی، خواندن وضعیت هر دو مجموعه از مسیر فقط‌خواندنی RPC پورت 3110 انجام می‌شود، چون سرور قدیمی 3108 اجازهٔ eth_getStorageAt نمی‌دهد. آدرس دارایی و حسابداری هر مجموعه مستقل می‌ماند.

خروجی شامل کاربران و ترتیبشان، معرف و فرزندان، عمق، رتبه‌ها، خریدها، اعتبارهای دو شاخه، مطالبات نقدی و اتوبای، صف‌ها و کارهای حجم، تاریخچهٔ دوره‌های تسویه، صندوق‌ها و اعتبارهای ماهانه، دفتر دارنده‌های توکن از جمله غیرعضوها، رکورد مجوزهای FTI، کد قراردادها، موجودی native آدرس‌های اصلی، ABI و artifact و سورس قراردادهای همان نصب است. کد باینری از روی سورس و solc موجود در حافظه دوباره کامپایل و bytecode آن با artifact نصب تطبیق می‌شود؛ سپس layout معتبر ذخیره می‌شود. این کار هیچ artifact فعال را بازنویسی نمی‌کند.

ابزار از exporter موجود استفاده می‌کند که در صورت دادهٔ تاریخی ناقص، حسابداری نامنطبق یا تسویه/کار حجم باز در بلوک انتخابی، خروجی کامل را رد می‌کند. هیچ مقدار ناموجودی صفر فرض نمی‌شود. snapshot جزئی یا FAILED.json جای بکاپ کامل نیست. اطلاعات ثبت‌شده پس از بلوک انتخاب‌شده داخل این snapshot نیستند؛ این ابزار نه بکاپ مستمر است و نه freeze.

## فایل‌ها و معیار موفقیت

پوشهٔ تازه زیر `/var/backups/fti-users` با دسترسی خصوصی ساخته می‌شود. مسیر هنگام شروع چاپ می‌شود. برای هر پورت مسیر log جداگانه چاپ می‌شود؛ خواندن تاریخچه ممکن است طولانی باشد. اجرای فرمان foreground است و قطع نشست می‌تواند آن را متوقف کند. هم‌زمان دوباره اجرا نکنید.

فقط بعد از تکمیل تمام پورت‌های انتخاب‌شده، آرشیو `fti-users-snapshot.tar.gz` و فایل checksum ساخته می‌شوند. آرشیو در پوشهٔ موقت جدا باز، هش تمام فایل‌ها کنترل و روابط کاربران و مجموع عرضه/مطالبات/اعتبارها دوباره از دادهٔ بازگردانده‌شده بررسی می‌شوند.

نتیجهٔ نهایی باید `FTI_USERS_BACKUP_SAVED` و `archiveRestoreCheck: PASS` باشد. `result.json` تعداد واقعی رکوردهای همان snapshot و آدرس فایل را گزارش می‌کند؛ تعداد کاربران از عکس یا دادهٔ آزمایشی hardcode نشده است.

**archiveRestoreCheck فقط بازشدن و سلامت محتوای آرشیو است، نه بازیابی روی EVM.** مقدار `evmRestoreTested` صریحاً false است. قراردادها freeze نمی‌شوند؛ سرویس ری‌استارت نمی‌شود؛ پولی انتقال نمی‌یابد. backup، مجوز واردکردن داده به قرارداد یا تضمین بازیابی وجه نیست. محدودیت برداشت پشتوانهٔ باینری legacy هم با گرفتن فایل حل نمی‌شود.

این آرشیو بکاپ دیتابیس خارج از زنجیره، کلیدهای شورا یا نصب کامل سیستم‌عامل نیست. فایل‌های خصوصی روی گیت‌هاب یا داخل مسیر عمومی سایت منتشر نمی‌شوند. آرشیو فعلاً فقط روی همان سرور و بدون رمزگذاری محتوایی قرار می‌گیرد؛ دسترسی فایل محدود است. یک نسخهٔ رمزگذاری‌شده در محل مستقل، جداگانه لازم است و این ابزار انتقال خارج از سرور را انجام نمی‌دهد. برای بررسی در چت، فقط result.json یا پیام خطای کوتاه کافی است، نه خود آرشیو کاربران و نه فایل‌های کلید.

## شواهد این نوبت

- بررسی syntax Python و Node و ده تست Python کنترل داده، مقادیر صحیح، آرشیو خصوصی، فایل تکراری و symlink: موفق.
- صادرکنندهٔ واقعی با دو نمونهٔ قرارداد روی Ganache آزمایش شد: مدل Upgradeable و مدل legacy؛ هرکدام 31 عضو و 32 ورودی دفتر توکن، شامل یک دارندهٔ غیرعضو. خروجی، تطبیق حسابداری و bytecode/layout موفق بود.
- داده‌های همین دو نمونه در آرشیو قرار گرفتند و roundtrip فایل‌ها، هش‌ها و اعتبارسنجی مجدد موفق بود. این اعداد متعلق به نمونهٔ محلی‌اند؛ نه کاربران سرور مالک.
- یک اجرای آزمایشی اولیه از محدودیت زمان ابزار محیط نویسنده عبور کرد؛ اجرای جداگانه و سپس اجرای نهایی هر دو مدل کامل شد. تست شکست‌خورده یا نیمه‌تمام به‌عنوان مدرک کامل استفاده نشده است.
- نسخهٔ قابل‌اجرای تست EVM در `test/recovery-snapshot.test.mjs` و آزمون‌های Python در `test/recovery-snapshot.test.py` ثبت شده‌اند. نتیجهٔ CI جدید جداگانه است و صرف ثبت فایل به معنی موفقیت آن نیست.
- از محیط نویسنده، DNS و اتصال به سایت فعال برقرار نشد و اتصال SSH موجود به همان VPS هم در دسترس نبود. هیچ backup از دادهٔ واقعی سرور در این نوبت گرفته یا دریافت نشده است.
