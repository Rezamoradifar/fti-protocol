# FTI — مسیر نصب تا فعال‌سازی با حفظ کاربران

این راهنما برای ادامهٔ نصب موجود است، نه ساخت Genesis جدید. دستور آماده‌سازی اجرایی است؛ بخش ارتقا و اتصال نسخهٔ زنده، چک‌لیست اجرایی و شروط پذیرش است و نباید با نصب‌کنندهٔ کاملِ فعال‌سازی اشتباه شود. هنوز چنین نصب‌کنندهٔ کامل و تأییدشده‌ای برای ترکیب قراردادهای قبلی با این نسخهٔ جدید وب/Keeper تحویل نشده است.

## دامنهٔ این نسخه

اتوبای انتخابی ۵ تا ۱۰۰ درصد از درآمد ساعتی باینریِ بیلدر، حذف کنترل حداکثر قیمت اتوبای، حفظ مطالبات قبلی و درخواست بستن چهار صندوق ماهانه در مرز ماه میلادی پیاده‌سازی شده‌اند. ترجمهٔ کامل هفت زبان، لینک‌های رسمی شبکه‌های اجتماعی و اصلاح نمودار در این انتشار نیستند.

## اصلاح لازم پیش از نصب

اجرای Global Builder controls شمارهٔ 38136101625 روی head برابر 7d6f6a2ab0ac3265bfe86b66f93fd3d4dd8c88c3، تعداد ۴۸ تست موفق و یک شکست ثبت کرد. شکست در continuity-deployment به علت نبود web/app.js بود: releaseManifest فایل ساخته‌شدهٔ وب را می‌خواند، ولی workflow و نصب‌کننده build:web را بعد از تست قرار داده بودند. این خطای ترتیب بود؛ محلی که قبلاً bundle داشت آن را نشان نمی‌داد.

ترتیب در نصب‌کننده و CI به نصب وابستگی‌ها، کامپایل، کنترل storage، build وب و سپس تست اصلاح شد. آزمون shell نیز اکنون پیش از --test وجود فایل ساختگی web/app.js را مطالبه می‌کند و ترتیب workflow را جداگانه کنترل می‌کند. تست حذف یا کنترل صحت نسخه دور زده نشده است.

اعتبارسنجی این اصلاح در محیط نویسنده: کامپایل واقعی Solidity، build واقعی وب، کنترل storage و ۱۳ تست مرتبط موفق شدند؛ ۱۲ تست ابزار shell و یک آزمون واقعی استقرار/API روی Ganache. این اجرای ۱۳تایی کل تست‌های مخزن نیست. نتایج CI برای commit جدید باید جداگانه خوانده شوند. هیچ تراکنش عمومی، تغییر سرویس یا انتقال وجه در این اصلاح انجام نشده است.

## ۱. نصب نسخهٔ آمادهٔ بررسی

در همان سرور لینوکسی با Bash، git، curl، sha256sum و Node 22 یا جدیدتر اجرا کنید. مسیر شناخته‌شدهٔ runtime موجود در /opt/fti/runtime بررسی می‌شود؛ یا FTI_NODE_BINARY را به Node نصب‌شده بدهید. این راهنما دستور نصب کورکورانهٔ Node یا تعویض runtime سرویس فعلی ندارد.

```bash
(
  set -euo pipefail
  umask 077
  REV='e3c379a9bf48476849d8f5881ea9dc507a251423'
  FILE="$(mktemp)"
  trap 'rm -f "$FILE"' EXIT
  curl -fL --retry 2 --connect-timeout 15 --max-time 120 \
    "https://raw.githubusercontent.com/Rezamoradifar/fti-protocol/$REV/tools/prepare-builder-controls.sh" \
    -o "$FILE"
  printf '%s  %s\n' \
    'e4fce2e7cdf9bb8e7902e17379741e54046d96a1997bfd76e13440e4c323713d' \
    "$FILE" | sha256sum -c -
  bash "$FILE" "$REV"
)
```

REV نسخهٔ دقیق شامل اصلاح نصب و تست‌هاست. دریافت، نصب و تست در پوشه‌ای تازه زیر $HOME/fti-candidates انجام می‌شود. هیچ checkout فعال، deployment، سرویس یا قرارداد تغییر نمی‌کند. برای جلسهٔ SSH ناپایدار از نشست مدیریت‌شدهٔ موجود روی سرور استفاده کنید؛ این فرمان foreground است و خودکار در پس‌زمینه اجرا نمی‌شود.

موفقیت با FTI_BUILDER_CANDIDATE_PREPARED مشخص می‌شود. مسیر candidate ابتدای log چاپ می‌شود و result.json کنار source قرار دارد. exitCode باید صفر، result برابر CANDIDATE_PREPARED و liveActivated و fundsMoved همچنان false باشند. این falseها خطا نیستند؛ مرز آماده‌سازی را نشان می‌دهند. با شکست هر مرحله ادامه ندهید و همان نسخه را روی سایت overwrite نکنید.

## ۲. شناسایی نصب واقعی و پشتیبان تنظیمات

آدرس یا مسیر نصب را از حافظه، نام جدیدترین پوشه یا نمونهٔ تست انتخاب نکنید. ابتدا سرویس فعال را ببینید:

```bash
systemctl list-units --type=service --state=running --no-legend --plain 'fti*-web.service' 'fti*-keeper.service'
```

در نصب‌های پروژه نام‌هایی مانند fti-continuity-web.service و fti-v3-web.service استفاده شده‌اند. نام را فقط از خروجی واقعی بردارید. بیش از یک سرویس فعال ممکن است به نسخه‌های متفاوت مربوط باشد؛ اول تطبیق آن با upstream سایت لازم است. دستور زیر نمونهٔ انتخاب نام است، نه تأیید اینکه همین سرویس روی سرور شما فعال است:

```bash
WEB_UNIT='fti-continuity-web.service'
systemctl show "$WEB_UNIT" -p ActiveState -p MainPID -p WorkingDirectory -p EnvironmentFiles -p FragmentPath -p DropInPaths
```

systemctl show -p Environment، فایل کامل .env یا environ فرایند را در چت منتشر نکنید. فایل deployment واقعی از DEPLOYMENT_FILE در تنظیمات همان سرویس می‌آید. از deployment و واحدهای systemd، فایل‌های محیطی، تنظیمات nginx، کد و artifact نسخهٔ قبلی نسخهٔ خصوصی با دسترسی 0600/0700 نگه دارید. فایل‌های کلید و RPC دارای رمز فقط روی سرور محفوظ بمانند. این بکاپ فایل‌های تنظیمات، بکاپ سازگارِ پایگاه دادهٔ زنده نیست؛ برای پایگاه داده باید روش snapshot مخصوص همان موتور انتخاب و بازیابی آزمایشی انجام شود.

این کد فقط بخش عمومی تنظیمات API محلی را نشان می‌دهد؛ نه امضا می‌کند و نه موجودی را تغییر می‌دهد:

```bash
python3 - <<'PY'
import json, urllib.request
keys = ('chainId','release','sourceRevision','binary','token','usd',
        'council','timelock','binaryContract','tokenContract',
        'binaryImplementation','tokenImplementation','selectableHourlyAutoBuy')
for port in (3110, 3108):
    try:
        with urllib.request.urlopen(f'http://127.0.0.1:{port}/api/config', timeout=10) as r:
            cfg = json.loads(r.read(2_000_001))
        if not isinstance(cfg, dict):
            raise ValueError('Expected object')
        public = {k: cfg[k] for k in keys if k in cfg and isinstance(cfg[k], (str, int, bool))}
        print(json.dumps({'port':port, 'config':public}, ensure_ascii=False, indent=2))
    except Exception:
        print(json.dumps({'port':port, 'status':'UNAVAILABLE_OR_INVALID'}))
PY
```

خروجی API به‌تنهایی اثبات وضعیت قرارداد نیست. قبل از عملیات باید chainId، آدرس proxy، implementation، هش bytecode، نقش‌های شورا، مقدار تأخیر و وضعیت واقعی حسابداری از RPC همان شبکه خوانده و با تنظیمات منبع تطبیق داده شوند. این انتشار فقط 97 و 31337 را برای ابزار مهاجرت می‌پذیرد، نه شبکهٔ اصلی 56.

## ۳. انتخاب مسیر قرارداد؛ دو کار را یکی ندانید

### همان آدرس، منطق جدید

برای فعال‌کردن اتوبای و ماه‌بندی جدید روی پروکسی موجود، implementation جدیدِ سازگار لازم است. این کار با نصب فایل وب یا تغییر ABI انجام نمی‌شود. قراردادهای فعلی پیش از ارتقا recoveryFrozen بودن هر دو جزء و مسیر حاکمیتی را مطالبه می‌کنند. طرح ارتقا باید چیدمان واقعی نسخهٔ قدیم و جدید، رویدادهای تراکنش ارتقا و دادهٔ کاربران قبل و بعد را بررسی کند. افزودن mapping درصد باید در حساب‌های قدیمی مقدار پیش‌فرض ۵ بدهد و هیچ مطالبهٔ قبلی را تغییر ندهد.

### آدرس جدید

ابزار scripts/migrate-addresses.mjs برای مهاجرت موجود است. اما مقصد در پایان مهاجرت به originalLogic ثبت‌شده بازمی‌گردد؛ جابه‌جایی آدرس، خودبه‌خود کد اقتصادی جدید را جایگزین منطق قدیمی نمی‌کند. برای منبع قدیمی و مقصد دارای قابلیت‌های جدید، مراحل مهاجرت و ارتقای منطق باید جداگانه با ABI و layout همان نسخه‌ها بررسی شوند. تست مهاجرت نمونه‌های تازه جای این تطبیق با قرارداد نصب‌شدهٔ کاربر نیست.

برای دیدن رابط واقعی ابزار، بدون خواندن کلید یا ارسال تراکنش:

```bash
node scripts/migrate-addresses.mjs --help
```

از فایل deployment اصلی و RPC آرشیوی معتبر استفاده کنید. preflight، deploy بدون --send، plan، export و verify حالت‌های خواندنی/تولید برنامه‌اند. copy و execute به --send، شناسهٔ شبکه، تأیید coordinator، بودجهٔ کارمزد، فایل خصوصی کلید و log مستقل نیاز دارند. آدرس coordinator فقط از رسید استقرار واقعی گرفته می‌شود. هیچ مقدار نامعلوم را با آدرس تست، صفر یا مقدار حدسی جایگزین نکنید. راهنمای آرگومان‌ها: docs/ADDRESS_MIGRATION_OPERATOR.fa.md.

## ۴. ترتیب اجرای حاکمیتی و مالی

قبل از هر مرحلهٔ دارای write، برنامه باید به آدرس‌های منبع فعلی و نسخهٔ بازبینی‌شده مقید و شبیه‌سازی شود. مبلغ گس جدا از پشتوانهٔ صندوق‌هاست.

| مرحله | شرط و نتیجه |
| --- | --- |
| آماده‌سازی انتشار | نسخهٔ جدید وب/Keeper باید قابلیت تأیید منشأ قرارداد پس از ارتقا را داشته باشد؛ قبل از توقف منبع راه خروج بررسی شود. |
| پایان کارهای باز | تسویهٔ ساعتی، ماهانه و jobهای حجم به وضعیت سازگار برسند. |
| Freeze کنترل‌شده | توقف تغییر وضعیت هر دو قرارداد؛ توقف یک دکمهٔ UI کافی نیست. |
| Snapshot کامل | ثبت بلوک و هش، تمام اعضا و دارنده‌های غیرعضو، اعتبارها، صف‌ها و مجموع پشتوانه؛ دادهٔ ناقص به صفر تبدیل نشود. |
| ارتقای همان‌آدرس یا arm/configure مهاجرت | عملیات فقط از قرارداد Timelock مبدأ، با تأیید ۵ از ۷ شورا و تأخیر حداقل واقعی انجام شود. |
| Copy در مهاجرت | ورود دسته‌ای داده از منبع متوقف؛ ادامه از شمارندهٔ زنجیره، نه فایل محلی. COPY_COMPLETE به معنی انتقال پول نیست. |
| بررسی مستقل | اعضا، رتبه‌ها، مطالبات، عرضه و مالکیت بدهی‌ها قبل از commit تطبیق داده شوند. |
| Commit در مهاجرت | تحویل پشتوانهٔ هر دو جزء و بازنشستگی منبع در یک تراکنش؛ رسید باید موفق و مقادیر انتقال تطبیق‌شده باشند. |
| بررسی مقصد متوقف | بعد از commit، مقصد همچنان recoveryFrozen است. توقف آن را قبل از مقایسهٔ کامل برندارید. |
| Reopen | عملیات جداگانهٔ حاکمیتی پس از تأیید همهٔ شرط‌های مالی و آماده‌بودن انتشار سرویس. |

۷۲ ساعت حداقل تأخیر عملیات مشمول است؛ کل زنجیرهٔ مهاجرت الزاماً ۷۲ ساعت تمام نمی‌شود. ارسال پیشنهاد با امضای یک عضو، جای پنج تأیید را نمی‌گیرد. هیچ seed phrase یا کلید شورا نباید در گیت‌هاب، چت یا log قرار گیرد.

## ۵. اتصال وب و Keeper؛ بخش تکمیل‌نشدهٔ نصب خودکار

scripts/continuity-release.mjs در این نسخه هم fingerprint و artifact را کنترل می‌کند و هم تراکنش‌های ایجاد اولیه را با build بررسی می‌کند. بعد از ارتقا یا ساخت proxy مقصد توسط coordinator، metadata نصب تازهٔ قبلی لزوماً با این بررسی سازگار نیست. صرف تغییر آدرس‌ها، sourceFingerprint یا constructorArgs راه معتبر فعال‌سازی نیست.

مسیر انتشار باید سابقهٔ ایجاد اصلی، رسید ارتقای مجاز/مهاجرت، آدرس implementation نهایی، هش کد و ABI جدید را به‌صورت معتبر به هم متصل کند. این سازگارسازی همراه با آزمون سرویسِ پس از ارتقا هنوز در این اصلاح نصب اضافه نشده است. بنابراین تا آن مرحله تکمیل و روی نمونهٔ همسان آزمایش نشود، دستور restart کورکورانهٔ سرویس فعال یا سوئیچ nginx ارائه نمی‌شود.

پس از فراهم‌شدن این مسیر: نسخهٔ کاندید وب روی یک پورت محلی آزادِ جدا، بدون تغییر upstream فعلی راه‌اندازی شود؛ /health، /api/config، /api/state و ABIها بررسی شوند؛ سپس تنها upstream همان سایت با nginx -t و reload کنترل‌شده جابه‌جا شود. Keeper فقط به همان deployment تأییدشده متصل شود و worker قدیمی نباید هم‌زمان روی منبع بازنشسته کار کند. این مراحل، دستور آمادهٔ اجرا برای وضعیت ناشناختهٔ سرور نیستند.

## ۶. پذیرش نهایی و بازگشت

آماده‌سازی وقتی تمام است که result.json موفق باشد. فعال‌سازی وقتی تمام است که علاوه بر آن، implementation شبکه و شناسهٔ انتشار وب/Keeper درست باشند، داده‌های تمام کاربران و مجموع بدهی‌ها تطبیق کنند و رسیدهای لازم وجود داشته باشند. روی نمونهٔ مستقل باید پرداخت نقدی و اتوبای دقیقاً یک‌بار، درصدهای ۵ و میانی و ۱۰۰، عدم تغییر مطالبات قبلی، درخواست زودهنگام ماه، تغییر ماه‌های ۲۸/۲۹/۳۰/۳۱روزه و قطع/ادامهٔ Keeper بررسی شوند. موفقیت /health به‌تنهایی تأیید مهاجرت نیست.

بازگشت فایل‌ها و nginx با بازگشت بلاک‌چین فرق دارد. پیش از commit مهاجرت، abort حاکمیتی ممکن است. پس از commit، منبع بازنشسته نباید با فایل بکاپ دوباره قابل‌خرج شود. rollback وب تنها باید به نسخه‌ای باشد که قرارداد فعلی را درست می‌خواند؛ به ABI یا deployment قدیمیِ نامعتبر برنگردید. همچنین وجود BNB یا FTI متعلق به خود آدرس‌های منبع و قراردادهای legacy غیرپروکسی در ابزار فعلی شرایط توقف‌اند، نه مجوز نادیده‌گرفتن دارایی.

**وضعیت تحویل:** اصلاح نصب تمیز و راهنمای کامل مراحل ثبت شده است؛ فعال‌سازی زنده، انتقال دارایی کاربر، تکمیل اتصال انتشار پس از ارتقا و سه قابلیت ظاهری باقی‌مانده ادعا نشده‌اند.
