# آماده‌سازی شبکه اصلی FTI — ۱۳ اکتبر ۲۰۲۶

این شاخه از `bd924e428debd5d284e08fd2448d0d271c5bf9c7` جدا شده تا آماده‌سازی شبکه اصلی، فرمان تست‌نت در حال اجرای کاربر را تغییر ندهد. هدف شبکه اصلی BNB با شناسه ۵۶ است. هیچ کلید خصوصی دریافت، تراکنش عمومی ارسال، سرویس فعال تعویض یا موجودی کاربر حذف نشده است.

## موارد پیاده‌سازی‌شده

| بخش | رفتار |
| --- | --- |
| تنظیم شبکه | شبکه اصلی فقط با مدل Upgradeable، نام انتشار مخصوص شبکه اصلی و حالت `bnb-mainnet` پذیرفته می‌شود؛ تغییر صرف chainId تنظیم تست‌نت کافی نیست. |
| اتصال ولت | WalletConnect و ولت مرورگر شبکه ۵۶ یا ۹۷ را صریح انتخاب می‌کنند. تراکنش پس از بررسی شبکه ولت آغاز می‌شود؛ لینک‌ها به اکسپلورر همان شبکه می‌روند. |
| رابط کاربری | عنوان شبکه و دارایی‌ها وابسته به تنظیمات بررسی‌شده است. دریافت MockUSD و ABI آن روی شبکه اصلی ارائه نمی‌شود. صفحه عمومی نیز برچسب و آدرس شبکه اصلی را از API می‌خواند. |
| انتشار سرویس‌ها | وب، Keeper و پایش شبکه اصلی، نسخه ساخته‌شده، کد قرارداد، اسلات implementation، ورودی ساخت، رسید و بلوک ساخت، نقش‌ها، شورا، Timelock و حساب‌ها را بررسی می‌کنند. |
| استقرار | برنامه‌ریز هفت تراکنش بدون امضا برای قرارداد جدید می‌سازد. فایل ورودی همچنان آدرس واقعی پشتوانه ۱۸ اعشاری، هش کد، deployer، توسعه، هفت عضو شورا و ۳۱ جایگاه آغازین می‌خواهد. این مسیر جایگزین انتقال کاربران موجود نیست. |
| تأیید پس از استقرار | `finalize-mainnet.mjs` هفت هش مستقل را با payload بازسازی‌شده، فرستنده، nonce، شبکه، مقدار، رسید موفق، آدرس و بلوک تطبیق می‌دهد؛ سپس تنظیم قابل بررسی سرویس را می‌سازد. تعداد تأییدها شرط دریافت رسید است و اثبات قطعی نهایی‌شدن زنجیره نیست. |
| بررسی انتقال | `review-mainnet-migration.mjs` خروجی کامل بلوک ثابت تست‌نت را با هش فایل می‌خواند؛ ارتباط درخت، دفتر موجودی، تعهدات نقدی، خرید خودکار و اعتبارها را تطبیق می‌دهد. خروجی فقط گزارش آفلاین است؛ importer شبکه اصلی یا اثبات روی زنجیره نیست. |

قراردادهای Solidity و درصدها و قواعد اقتصادی در این شاخه تغییر نکرده‌اند. نام دارایی در رابط به‌تنهایی هویت یا ارزش دلار آن را اثبات نمی‌کند؛ آدرس پشتوانه باید پیش از استقرار انتخاب و بررسی شود. مستندات رسمی شبکه: https://docs.bnbchain.org/bnb-smart-chain/developers/wallet-configuration/

## اجرای آماده‌سازی روی سرور

`tools/prepare-mainnet-candidate.sh FULL_REVIEWED_SHA` در مسیر خصوصی جدید `/var/tmp/fti-mainnet-candidate.*` نسخه ثابت را دریافت می‌کند، وابستگی‌ها، قراردادها، وب و لندینگ را می‌سازد و آزمون‌های یکپارچه شبکه اصلی شبیه‌سازی‌شده و سازگاری تست‌نت را اجرا می‌کند.

نتیجه در `result.json` ثبت می‌شود. `MAINNET_CANDIDATE_PREPARED` به معنی موفقیت ساخت و تمرین محلی است؛ همواره `submitted:false`، `servicesActivated:false` و `readyToBroadcast:false` باقی می‌ماند. فایل‌های `*.REQUIRED.*` نمونه‌اند و بدون ورودی واقعی قابل اجرا نیستند. این فرمان به RPC عمومی وصل نمی‌شود و کلیدهای سرویس فعلی را نمی‌خواند.

## گزارش انتقال کاربران

پس از موفقیت بکاپ تست‌نت، از `snapshot.json` همان بکاپ و SHA-256 بررسی‌شده آن استفاده شود:

```bash
node scripts/review-mainnet-migration.mjs \
  --snapshot /PRIVATE/VERIFIED_BACKUP/snapshot.json \
  --sha256 REVIEWED_SNAPSHOT_SHA256 \
  --out /PRIVATE/NEW_MAINNET_MIGRATION_REVIEW.json
```

این فرمان تغییری در منبع ایجاد نمی‌کند. مبلغ `totalReplacementCollateralWei` جمع پشتوانه داخل دو قرارداد مبدأ است، با واحد پایه ۱۸ اعشاری، برای بررسی سناریوی حفظ کامل همان دفتر مالی. این رقم مانده ولت‌های بیرونی را شامل نمی‌شود، الزاماً بودجه نهایی سناریوی منتخب نیست و تأمین وجه مقصد را اثبات نمی‌کند. خرج‌کردن دارایی تست‌نت، پشتوانه شبکه اصلی ایجاد نمی‌کند. مجوزهای ERC20 رضایت کاربران به آدرس جدید محسوب نمی‌شوند.

انتخاب اقتصادی حل‌نشده است: فقط ولت و درخت با شروع مالی جدید، یا حفظ حقوق و دفتر مالی با تأمین پشتوانه واقعی؟ این انتخاب روی واحدهای خریداری‌شده، رنک، carry، اعتبارها، توکن‌ها و صندوق‌های ماهانه اثر می‌گذارد و نباید از تغییر شبکه استنباط شود. تا تعیین این سیاست، گزارش `UNDECIDED` و `readyToImport:false` دارد. قراردادهای مهاجرت فعلی فقط داخل یک زنجیره کار می‌کنند؛ importer ۹۷ به ۵۶ در این تحویل ایجاد نشده است.

## فرمان‌های بدون امضا و تأیید استقرار

برای یک استقرار جدید که ورودی و سیاست آن جداگانه تأیید شده باشد:

```bash
export FTI_MAINNET_RPC_URL='YOUR_PRIVATE_MAINNET_RPC'
node scripts/prepare-mainnet.mjs \
  --config /PRIVATE/REVIEWED_PUBLIC_ADDRESSES.json \
  --out /PRIVATE/NEW_UNSIGNED_PLAN.json
```

فایل طرح به nonce و همان commit/build وابسته است. ابزار امضا یا ارسال ندارد. پس از اجرای واقعی تراکنش‌ها توسط فرایند مجاز و ثبت هفت هش:

```bash
node scripts/finalize-mainnet.mjs \
  --plan /PRIVATE/REVIEWED_UNSIGNED_PLAN.json \
  --transactions /PRIVATE/ACTUAL_TRANSACTION_HASHES.json \
  --out /PRIVATE/NEW_VERIFIED_MAINNET_DEPLOYMENT.json
```

این ابزار نیز سرویس را فعال نمی‌کند. نمونه تنظیم سرویس در `config/mainnet-services.env.example`، پورت جدا ۳۱۱۲ و فایل deployment جدید دارد. کیف‌پول Keeper تنها gas دارد و اختیار شورا ندارد؛ کلید آن باید در فایل خصوصی جدا روی سرور تنظیم شود. بازگشت وب به تنظیم تست‌نت، تراکنش‌های قطعی شبکه اصلی را برنمی‌گرداند؛ به همین دلیل فعال‌سازی و تغییر دامنه اینجا انجام نمی‌شود.

## شواهد و مرز آمادگی

آزمون یکپارچه، هفت payload را روی EVM محلی با chainId شبیه‌سازی‌شده ۵۶ اجرا کرد و وب واقعی HTTP، API، خرید، فروش، سوزاندن ۳٪ انتقال، Keeper و مانیتور را بررسی کرد. نسخه اصلی ابزار همچنان هیچ تراکنشی ارسال نمی‌کند. آزمون‌ها ورودی دستکاری‌شده، شبکه اشتباه، رسید کم‌تأیید، هش ناسازگار، مالکیت نامتوازن و درخت خراب را رد می‌کنند.

اجرای محلی مجموعه اصلی این شاخه با ۷۱ تست موفق، صفر شکست و صفر تست لغوشده یا ردشده تمام شد. ساخت وب، لندینگ و بررسی نحوی Bash موفق بود. نتیجه CI یک commit دیگر جایگزین نتیجه CI این commit نیست. آمادگی فنی محلی به معنی دیپلوی عمومی، تکمیل مهاجرت یا ممیزی مستقل نیست. ورودی واقعی شبکه اصلی، گزارش نهایی بکاپ کاربر، سیاست مالی انتقال و importer متناظر هنوز برای مسیر کاربران موجود لازم‌اند.

دو ناسازگاری در بررسی تکمیلی نسخه قدیمی پیدا و اصلاح شدند: کنترل نام انتشار Keeper دوباره پیش از نیاز به کلید انجام می‌شود، و مسیر قدیمی API رویداد که RPC مستقل دارد رفتار قبلی خود را حفظ می‌کند. کنترل‌های اختصاصی شبکه اصلی در هر دو مسیر همچنان اجباری‌اند. مجموعه نهایی ۷۱ تست، این دو مورد را نیز پوشش داد.
